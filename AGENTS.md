# Agent instructions (OpenHands, Claude Code, any agent)

## Mission
Build the Amazing Goats platform from `tasks/BACKLOG.md`, one task card at a time, with a human reviewer in the loop.

## Ground rules
1. Work only on the task card you were given. Read its `files`, `acceptance` and `gate` fields first.
2. Branch name: `agent/<task-id>-<slug>`. Never push to `main`. Open a PR using the template.
3. Write or update tests with every change. Run `pnpm -r test` and `pnpm -r lint` (TypeScript) or `pytest` (Python services) before opening a PR.
4. Money is integer cents (ZAR). Times are stored in UTC and shown in Africa/Johannesburg. Prices in the database exclude VAT; VAT (15%) is added at display and invoice time.
5. Every table, endpoint and screen must respect RBAC (`packages/rbac`). Use `@RequirePermissions(...)` on every controller route.
6. Never read or write `.env`, secrets, or production data. Use `.env.example` and seed data.
7. No new dependency, no schema migration edit after merge, and no change to gated paths without the human approval label.

## Human approval gates (label `human-approved` required to merge)
- `db/migrations/**` (new migrations are fine as PRs; edits to merged files are forbidden)
- `packages/rbac/**`, auth, session and identity code
- `services/payments/**` and any money movement, refunds, payouts, reconciliation
- `services/accounts/**` credit limits, tiering and collections logic
- pricing, VAT and promotion logic in `services/commerce/**`
- `infra/**`, `.github/**`, deployment and environment configuration
- legal and regulatory text: terms, privacy, labels, ad policy, compliance copy
- anything that sends email, WhatsApp or SMS to real people

## Definition of done
Tests pass, lint passes, docs updated if behaviour changed, PR description lists what changed, risks, and how to verify. For UI work include a screenshot or wireframe reference from `docs/wireframes/index.html`.

## Compliance reminders
POPIA (consent, minimal personal data, access logging), Consumer Protection Act, R146 food labelling and advertising rules, Agricultural Product Standards Act packing and marking, Meat Safety Act. See `docs/07-compliance.md`. If unsure, stop and ask in the PR.

## Style
TypeScript strict, small modules, pure functions for business rules, DTO validation with class-validator, OpenAPI for every service, conventional commits.

## Agent workflow note
When branching from `main`, do not run `git reset --hard` (or `git checkout -f`) while the working tree has uncommitted edits to already-tracked files: it discards them, and a later commit then contains only newly-added files. Commit or `git stash -u` first, and check `git status` is clean before switching branches.

## Session learnings
- **Optional Nest dependencies need a token.** A bare constructor parameter that is not a provider makes Nest throw `Nest can't resolve dependencies of X (..., ?)` and the service never boots. Inject optional collaborators as `@Optional() @Inject(SOME_TOKEN) x: T = default`, and provide `{ provide: SOME_TOKEN, useFactory: ... }`. This bit `PermissionsGuard`, `AccessService` (clock) and `MfaService` (issuer).
- **Share one store instance** between a request interceptor and an API that reads it: declare the provider in the owning module and `exports:` it, rather than declaring it in both.
- **Pure rules + a store boundary.** Keep business rules as pure functions (no I/O, clock passed in) and put persistence behind an interface with an in-memory default. That is what makes them unit-testable without a database.
- **A root `vitest.config.*` is inherited by every workspace** that has no config of its own, and its `test.include` silently overrides their discovery (e.g. a service with 4 specs reported "No test files found"). Keep the root test's config out of auto-discovery: name it `vitest.bootstrap.config.mjs` and run it explicitly (`vitest run --config ...`).
- **`pnpm` may be reachable only through `corepack`.** `pnpm/action-setup` in CI and `corepack enable` locally put it on `PATH`; a bare `corepack pnpm test` does not, so a nested `pnpm` inside a script fails with "pnpm: not found". Enable corepack shims before running the full sequence.
- **Postgres is available via Docker** (`sudo docker run postgres:16-alpine`). Migrations are not idempotent, so apply them to a fresh database; `db/tests/rls.sql` runs through `scripts/test-rls.sh` and the CI `db` job.
- **Local monorepo runner:** `tsc --noEmit -p tsconfig.json` for lint and `vitest run` per package/service/app; build a package (`tsc -p packages/x/tsconfig.json`) before a service that imports its `dist` can boot. `dist/` is gitignored.
- **Merge workflow used:** branch `agent/<task>-<slug>` → push → `create_pr` with labels `agent-pr,human-approved` → mark ready → wait for `ci` and `agent-gate` → merge via `PUT .../merge-async` (poll the uuid) → `git fetch origin main && git reset --hard origin/main`.
- **Four-eyes belongs in a pure rule, not only the guard.** A `@RequirePermissions('pricing:approve')` guard checks the role, not that the approver differs from the requester. Enforce `approvedBy !== requestedBy` in the domain (`publish` in `pricing.rules.ts`) so it holds regardless of transport, and add a test asserting the permission stays in `TWO_PERSON` (`packages/rbac`).
- **Half-open validity windows.** Price lists (and anything time-boxed) use `[validFrom, validTo)`: live when `validFrom <= at < validTo`. This stops two versions overlapping on the boundary. When several are live, pick the latest `validFrom`.
- **Infra manifests are code, so pin them with a test.** The Northflank template (`infra/northflank/project.json`, `apiVersion` `v1.2`, a `Workflow` of nodes) and the Koyeb compose file (`infra/koyeb/koyeb-compose.yaml`) are the only description of production, and nothing else fails when they drift. `infra/deploy.spec.mjs` (run by `pnpm test` via `vitest.deploy.config.mjs`) reads them and asserts each service builds a Dockerfile that exists, its port equals the `PORT` default in `main.ts`, its health path is one the app serves, and no secret is a literal. Northflank node steps nest under `spec.spec.steps`, so the walker must recurse over every value, not just `spec`.
- **Secrets stay out of the repo.** The Northflank template reads credentials from `arguments` (`${args.*}`) into a secret group that also links the Postgres and Redis addons to `DATABASE_URL`/`REDIS_URL`; the Koyeb file references Koyeb secret names. Deploy the launch topology from `docs/01-architecture.md`, not all ten services.
- **Observability is a shared package, not per-service copy-paste.** `packages/observability` holds the log redaction, the temperature-breach rules, the alert router and the health-report shape as pure functions, each with its own spec. Services and apps depend on it; `createLogger` writes one JSON line to stdout and redacts any credential- or personal-data-looking key at any depth (logs leave the platform, so POPIA applies). Keep new cross-cutting rules here rather than re-implementing them.
- **Every deployable serves `GET /health`.** Nest services return `healthReport(...)` from a controller; Next.js apps return it from `app/health/route.ts`. `infra/deploy.spec.mjs` requires the probe path to be `/health` and the matching file to exist, so add the route when you add an app.
- **Idempotency belongs in a pure rule, keyed on the request.** Payment intents are created from an idempotency key (`createIntent`); the same key returns the stored intent, so a retried request or a double-click charges once. A key reused with a different amount throws rather than returning the first intent, because that hides a real mismatch. The provider-neutral `PaymentProvider` interface (`supports`/`createPayment`/`refund`/`verifyWebhook`) keeps intents, routing and webhooks from branching on the provider name.
- **Verify webhook signatures over the raw body, and reject replays.** `verifyHmacSignature` checks `t=<unix>,v1=<hex>` where `v1` is `HMAC-SHA256(secret, "<t>.<rawBody>")`, compares in constant time (`timingSafeEqual`), and rejects a timestamp outside a short window, so a captured body cannot be replayed. Deduplicate a verified event on `(provider, event_id)` (the unique key on `payments.provider_events`) and treat an out-of-order transition as a no-op rather than an error, so the provider is not asked to resend. Webhook routes stay off the RBAC guard: the provider authenticates with its signature.
- **Read the request body as text on a webhook route.** The signature is over the exact bytes received; if Nest parses and re-serialises JSON first, the HMAC no longer matches. Accept the body as a string and let the adapter `JSON.parse` it.
- **Consent is a rule, not a per-send check.** Outbound messages go through one `decideConsent` (`services/notifications/src/consent`): transactional messages about an order a person placed need no consent; marketing needs an opt-in for that exact channel, and an unknown contact is never sent marketing. Keep the gate in one place so every channel inherits it. Sending to a real person is a gated path (`gate:outbound`).
- **Render copy as data with a pure function, and fail on a missing value.** Templates are a subject and body holding `{{key}}` placeholders (`services/notifications/src/templates`). `render` throws `MissingPlaceholderError` rather than substituting an empty string, so a customer never gets "Hi , your order ...". Format money from integer cents (`formatZar`) and times in Africa/Johannesburg, so the copy matches the cut-off engine.
- **A transport error is logged as a reason, not the raw error.** Dispatch records `sent`/`suppressed`/`failed` with a reason (`no_transport`, `transport_error`, `no_consent`, `unknown_contact`) and never stores the provider's error text, which could carry a credential into the log. One `MessageTransport` per channel; inject `fetchFn` so the real request path is tested without contacting a provider.
- **`vi.fn` loses call-argument types.** `fetchFn.mock.calls[0]` is typed `[]` and `mock.calls[0][1]` fails to cast to `RequestInit`. Push `{ url, init }` into a typed array inside the fake instead of reading `mock.calls`.
- **A provider signature scheme belongs inside the adapter.** PayFast signs with an MD5 over the ordered, non-blank `name=urlencoded(value)` pairs plus a trailing `passphrase=` pair (`payfast-signature.ts`), which is neither the HMAC scheme the interface assumes nor PayFast's alphabetical "API signature" — mixing the two gives a mismatch that is hard to see. Its ITN is form-encoded, so parse the raw body as a form, not JSON. A provider that takes the customer by form POST (not a redirect) returns `form: { action, fields }` from `createPayment`.
- **Fall back only from a failure that happened before a provider reference exists.** `withFallback` (`services/payments/src/routing/provider-fallback.ts`) tries the routed, configured providers in order, reusing the intent's idempotency key on each attempt so a retry cannot charge twice. Record the error's message, never the raw error object, which a provider may populate with a credential; answer `503` when every provider fails. A failure after a reference was returned is not retried, because the charge may already exist.
- **A GraphQL provider needs its own request shape, and a hosted page is not always a redirect.** Stitch is GraphQL (`POST https://api.stitch.money/graphql`): pay by bank is a `clientPaymentInitiationRequestCreate` mutation, a recurring debit a `clientPaymentConsentRequestCreate` (`type: CAPITEC_PAY_RECURRING`) mutation. Stitch includes *every* method enabled on the client in a request by default, so set `paymentMethods` explicitly or a pay-by-bank request silently offers card. It returns a hosted URL (`redirectUrl`), unlike PayFast's form POST — keep both shapes inside their adapter and let the caller read whichever field is present.
- **Svix signs differently from a plain HMAC.** Stitch delivers webhooks through Svix: `verifySvixSignature` (`services/payments/src/providers/webhook-signature.ts`) checks `svix-id`/`svix-timestamp`/`svix-signature` over `"<id>.<timestamp>.<rawBody>"` with `base64(HMAC-SHA256(base64(secret), signedContent))`, where the secret is the base64 part of a `whsec_` value. Any entry in the space-delimited `v1,<base64>` list passes (a secret can rotate), and the timestamp carries the same replay window as the HMAC check. Do not reuse `verifyHmacSignature` for this.

- **Cross-service journeys need a root e2e suite, wired like the other root suites.** Per-package tests never see two services at once, so the core journeys live in `tests/e2e/` and run through `vitest.e2e.config.mjs` (`test.include: ['tests/**/*.spec.ts']`), added to the root `test` script next to the bootstrap and deploy suites — and, like them, deliberately not named `vitest.config.*` so it is not inherited by the workspaces. The specs import service **sources** across package boundaries (`../../services/...`, `../../apps/...`); vitest transpiles them on the fly, and `@ag/shared-types`/`@nestjs/*` resolve from the package's own `node_modules`. Only the network is stubbed (`StitchProvider` takes a `fetchFn`), so routing, fallback, the Svix signature check and the status transitions are the real code. Keep the cross-service wiring in `tests/e2e/harness.ts` so a journey reads as the customer's steps, not as setup.
- **Money out is four-eyes, in one place.** Refunds and payouts above a limit must be approved by someone other than the requester. That rule is shared (`services/payments/src/money/money.rules.ts`): the limits are named constants (`REFUND_SECOND_APPROVER_LIMIT_CENTS`, `PAYOUT_SECOND_APPROVER_LIMIT_CENTS`) and `assertSecondApprover` **throws** rather than returning a flag, so a caller cannot forget to check it — the same reasoning as putting four-eyes in the domain, not only in the guard. `refunds:approve`/`payouts:approve` stay in `TWO_PERSON` with a test pinning them there.
- **Reconciliation reports, it does not throw.** `reconcileSettlement` matches a provider settlement to its `settlement_lines`; it reconciles only when every line resolves to a known payment and the lines sum exactly to `net_cents`. A mismatch returns a reason (`no_lines`, `lines_do_not_sum_to_net`, `unknown_payment`) and is recorded, because it runs as a nightly batch and one bad row must not abort the rest.
- **A Nest service needs a boot check, and vitest cannot give one.** `@nestjs/testing` is not a dependency, and vitest transpiles with esbuild, which does not emit `design:paramtypes`, so a `NestFactory.create(AppModule)` spec fails at collection (`Worker exited unexpectedly`). Boot the built app out of process instead (`tsc -p tsconfig.json` then `node` a throwaway that calls `NestFactory.create(AppModule)`) — it caught `ChargebacksService` unable to resolve its clock token. Optional collaborators must be `@Optional() @Inject(TOKEN) x = default`; a bare `@Inject(TOKEN)` with a default value still fails to resolve.
- **Put the row-level-security session in one package, not per service.** The one thing every SQL adapter must get right, and the one that is easy to get wrong, is the `app.org_id`/`app.user_id`/`app.staff` session. `@ag/db` owns it: `Db.withSession(context, fn)` opens a transaction, applies the settings with a parameterised `set_config(..., true)` (transaction-local, so a value cannot be injected and resets with the transaction), runs `fn`, then commits or rolls back. The application connects as a `NOSUPERUSER, NOBYPASSRLS` role; a superuser or a table owner bypasses the policies silently, so the `@ag/db` integration test provisions such a role and asserts scoping through it — asserting through a privileged connection would prove nothing.
- **Carry the request session in an `AsyncLocalStorage`, set it from the guard's caller.** A Nest middleware reads `userFromRequest(req)` and wraps the request in `runWithSession(...)`, so an adapter calls `currentSession()` without threading the context through every store signature. An unauthenticated request (a provider webhook, off the RBAC guard) gets an empty session, which is default-deny — the safe failure, not "see everything".
- **`selectStore(inMemory, buildSql)` keeps the driver switch lazy.** `STORE_DRIVER=memory` (the default) means a service boots with no database; only `STORE_DRIVER=sql` calls `buildSql()`, so the pool and the `DATABASE_URL` check never run for a memory-driver service. One switch for the whole service, so a deployment cannot persist half its stores.
- **The domain's opaque string ids must be `uuid`s at the schema boundary.** The payments domain used `ref_1`-style ids, but the schema has `uuid` primary keys and foreign keys. Use `randomUUID()` for ids and keep the business key (an idempotency key, a provider reference) as a column with a unique index, so a lookup still resolves the same row without a non-uuid id.
- **Adding a store to an existing module means the module factory needs a type argument and an optional `AG_DB`.** `selectStore(new InMemoryXStore(), () => new PgXStore(db!))` infers `T` from the in-memory class and then rejects the SQL class (it has no private maps). Pass the interface explicitly — `selectStore<XStore>(...)` — and inject the handle as `inject: [{ token: AG_DB, optional: true }]` with `useFactory: (db?: Db) => ...`, so the memory driver still resolves when the handle is `undefined`.
- **Converting a store to async ripples into every caller.** Making `IntentStore`/`WebhookStore` async forced `IntentsService.create`/`list`/`get`/`handleWebhook`, `WebhooksService.receive`/`list`, their controllers, and the root e2e journey to `await`. Grep the whole repo for the call sites (including `tests/e2e/`) before running the suite, or a `.received`/`.duplicate` read on a `Promise` fails at runtime, not compile time.
- **A shared persistence boundary beats a per-service copy.** The RLS/session wiring (`PersistenceModule`, `AG_DB`, `SessionMiddleware`) and the `isStaff` role check lived in `services/payments`; `services/accounts` needs the same, so they moved to `packages/nest-db` (and `isStaff` to `packages/rbac`). Payments was migrated onto the shared package in the same change. A service opts in with `imports: [PersistenceModule]` and `consumer.apply(SessionMiddleware).forRoutes('*')`, so the session is set before any store runs. Extracting a shared boundary is a gated change when the old home is gated (`services/payments/**`), so it needs the human-approved label.
- **One threshold, one definition.** `evaluateTier` already flags a limit above the approval threshold with `needsApproval`. The approval rules must not invent a second threshold: export `CREDIT_APPROVAL_THRESHOLD_CENTS` from `tiering.ts` and have `needsSecondApprover` default to it, so "needs approval" and "needs two approvers" cannot drift apart. The value is R100,000, matching the payments `REFUND_/PAYOUT_SECOND_APPROVER_LIMIT_CENTS` convention of a named constant that the rule reads.
- **A `@ag/db` integration test provisions its own `NOSUPERUSER, NOBYPASSRLS` role and connects as it.** A superuser or table owner bypasses RLS silently, so asserting scoping through the service's own connection would prove nothing. The accounts adapter test creates the role, grants schema usage and table/sequence privileges, seeds two orgs, and asserts an org sees only its own rows; it is gated on `DATABASE_URL` so the default unit run needs no database, and wired into the CI `db` job next to `@ag/payments`.
- **Reuse the existing entity for intake rather than a new table.** The trade application (T-024) writes to the `accounts.credit_applications` row and its documents to `accounts.documents`; migration 0014 only *adds* columns (registration number, declared turnover, POPIA consent, decision reason). The approval columns (`decision`/`decided_by`/`second_approver`/`decided_at`) were reused, so the intake and the credit-limit workflow share one lifecycle. A derived field (the NCA review flag) is recomputed on read from turnover rather than stored, so it cannot drift.
- **The frontend re-states the domain rule as a pure view helper.** `apps/trade-portal/lib/application.ts` mirrors `services/accounts/src/credit-applications/credit-application.rules.ts` (progress steps, document checklist, turnover bands, credit ladder) so the wireframed screens render from the same logic the API enforces, and both are unit-tested without a browser. Keep the shared thresholds as named constants on each side and pin them with tests on both.
- **A feature-flagged pilot is gated at registration and again at call time.** LulaPay (T-027) is registered by `providersFromEnv` only when `LULAPAY_ENABLED=true`, and `createPayment` refuses while `enabled` is false, so a stray route cannot reach the pilot while it is off. A pilot-only env key goes in the Northflank template `arguments` and `.env.example` even when its value is empty/false.
- **A minimum amount is enforced in routing and in the adapter.** Escrow is refused below `ESCROW_MINIMUM_CENTS` (R10,000) by `routePayment` *and* by `TradeSafeProvider.createPayment`, so a caller that bypasses routing still cannot open a sub-minimum escrow. A provider that signs the body directly (LulaPay) uses `verifyHmacBody` and deduplicates by event id; one that signs a timestamped envelope (TradeSafe, Peach) uses `verifyHmacSignature`.
- **A booted Nest app in vitest is possible once DI is explicit.** `design:paramtypes` is missing under esbuild, so a constructor parameter with no decorator resolves to `undefined`. Decorate every injected parameter (`@Inject(TOKEN) x: T`) — including ones that used to rely on the type, like the rate-limit guard's optional limiter — and `NestFactory.create(AppModule)` runs in-process. That gives a real end-to-end HTTP test (listen on `127.0.0.1`, `fetch` the routes) with only the network boundary stubbed, which the out-of-process boot check cannot. `app.listen(0, '127.0.0.1')` avoids the container's IPv6-only `::1` bind that fails a `fetch` with `EADDRNOTAVAIL`.
- **A catch-all proxy controller is registered after every owned route, and claims the rest.** The gateway forwards `/commerce`, `/ads`, `/accounts` (and the other service prefixes) with one `@All('*')` controller; importing its module **last** in `AppModule` puts its route after `/health`, `/gateway/auth`, `/gateway/bff` and `/gateway/rate-limit`, so a path the gateway owns always wins. A path no prefix matches answers 404 rather than being forwarded. The prefix map is pure (`proxy.routes.ts`); the upstream addresses come from the same `<NAME>_URL` map the BFF uses. Strip the `x-ag-*` identity headers at the edge so a caller cannot widen its own RLS scope; the owning service re-derives identity from the bearer token. Read the body from `req.body ?? req.rawBody` (boot with `rawBody: true`) so a forwarded write is not dropped.
- **The external "Kilo Code Review" check is not blocking.** It fails on every PR (including merged ones); mergeability is decided by the `ci` (`gate`/`node`/`python`/`db`) and `agent-gate` checks plus the `human-approved` label. Create the PR as a draft, then `gh pr ready` before the async merge, since `merge-async` rejects a draft.
- **The ad label is set by the server, not the caller.** `serveAds` (`services/ads/src/decisioning/serve-ads.ts`) wraps every pick in `sponsored: true` and a `label`, and the storefront `placeAds`/`isRenderableAd` drop anything unlabelled before it renders, so a page cannot accidentally show an unmarked ad. `eligibleCandidates` reuses the same `canGoLive` gate the advertiser sees, so a campaign that is not approved cannot be served by a second code path.
- **One fee schedule, one settlement schedule, and a place for the written quotes.** Provider fees and settlement terms are a single reviewed table each (`services/payments/src/routing/provider-fees.ts`, `settlement-terms.ts`); `estimateFeeCents` applies a model in one place and `route-payment.ts` delegates, so a rate change is a one-line edit. Each entry carries a `quoted`/`confirmed` flag and a `source`; `unquotedFeeModels`/`unconfirmedSettlementTerms` list what a human owes, and `quoteDrift` flags a signed quote that disagrees with the shipped figure. A gated `agent: human` task can still land its **code** as a draft PR — the missing written quotes are the human's, and the `agent-gate` check failing until `human-approved` is correct behaviour, not a bug.
- **A task card's `files:` glob tells you the gate.** `gate: none` + `agent: backend` (T-029) merges on green CI; `gate: payments` + `agent: human` (T-031) touches `services/payments/**`, so the `agent-gate` check fails until the `human-approved` label is added and the PR must stay a draft. Check the card's `gate`/`agent` before deciding whether to merge.
- **Split multi-task work into one branch and PR per task.** When a session completes more than one card, commit each card's files to its own `agent/<task>-<slug>` branch off `main` (stage by path, not `git add .`), so each PR reviews and merges independently. Compute the LoC/new-file analysis per task with `git diff --numstat <merge>^ <merge>` and `--name-status | grep ^A`.
- **A compliance gate is a three-way decision, not a boolean.** Onboarding a dairy, produce or egg supplier (`services/commerce/src/onboarding/supplier-onboarding.ts`) resolves to `approved` / `pending` / `blocked`: a required document that was never lodged, or one lodged but not yet verified, leaves the supplier **pending**; a lodged document whose expiry has passed **blocks**; everything present, verified and in date approves. Model it as one pure `evaluateSupplierOnboarding` returning the lists (`missing`/`unverified`/`expired`/`expiringSoon`), so the API and an admin checklist read the same result rather than each re-deriving the rule.
- **Reuse the existing cycle engine for a new vertical.** Fresh-produce pre-orders are the same `eggsDairyProduceCycle` shape the cycle engine already schedules (`produce-cycles.ts` builds them off the Tuesday/Friday route with the 48-hour cut-off), so dairy and produce inherit the tested cut-off/open-close behaviour instead of a second scheduler. Keep the route days and cut-off as named constants and assert the boundary (a cycle whose cut-off has passed is closed) in the spec.
- **A rule-set field and a per-pack field are different gates.** The R146 label generator (`services/commerce/src/compliance/label.ts`) separates the fields a **product** must carry (product name, net weight, country of origin, and — per rule set — an ingredient list, a class/grade, a pack-station number) from the fields added **per pack** at packing time (batch number, date marking). `missingLabelFields` checks a full label; `missingComplianceFields` checks only the rule-set extras the `product_compliance` row must hold. The "labels incomplete" report uses the latter, so batch/date do not flag every product as unfinished.
- **A `gate:` in the card is not the same as the `agent-gate` path list.** `agent-gate.yml` fails a PR only when it touches `db/migrations/`, `packages/rbac/`, `services/payments/`, `services/accounts/`, `infra/` or `.github/`. T-023 is marked `gate:rbac` yet touches only `apps/admin/**` and `services/identity/**`, so it merged without the `human-approved` label — a card's `gate:` records the review the human owes, not a CI block. T-032's `gate:legal` covers `services/commerce/**` + `docs/07-compliance.md`, neither of which is in the path list, so its label is a review note rather than a merge blocker. Check the path list before assuming a gate blocks the merge.
- **The label preview is data, and an unfilled field is a gate, not a blank.** `buildLabel` always renders the mandatory blocks; an unfilled one reads `[required: …]`, and `missing` lists what is outstanding, so a preview cannot hide a gap and a caller can gate on `valid`. Keep the generator pure so the API, an admin screen and a future print job agree on one definition; the regulation is summarised in `docs/07-compliance.md`, which stays explicitly "not legal advice".
- **Wire every portal to the gateway the same way, and keep the token on the server.** Each Next app gets one `lib/gateway.ts` that reads `GATEWAY_URL` and the `ag_token` cookie and builds `createClient(BASE_URL, () => ({ authorization: 'Bearer ' + token }))`; server components `await loadX()` and render, server actions (`app/**/actions.ts`, `'use server'`) do the writes, so the bearer token never reaches the browser bundle. A **client** component that must write (the driver's offline queue, the campaign builder) posts to a same-origin `app/api/.../route.ts`, which forwards to the gateway with the server-held token — the httpOnly cookie rides along automatically. Reduce each portal's seed module to `lib/fixtures.ts` (`git mv` to keep history) holding rows in the gateway's shape, so specs still exercise the real mapping/rendering code without a running gateway; keep the domain rules as pure view helpers and add a `lib/gateway.spec.ts` that asserts the form→API mapping. Check the card's `files:`/`gate:` first: T-050 (`gate: none`) touches only `apps/**` + `packages/api-client/**`, so it merges on green CI with no label.
- **Bridge the domain's string ids to the schema's uuids with an `external_id`, and join for the domain id.** The identity, logistics and stock services mint opaque string ids (`usr_...`, `batch_AG-YYYYMMDD-NNNN`, `r1`/`s1`/`e1`) while the schema keys on `uuid`. Migration 0016 adds a nullable `external_id` (unique) plus `*_ref` text columns for the actors a domain id cannot turn into a foreign key (a role's `granted_by`, a recall's `opened_by`, a driver event's `stop`). Where a real foreign key is still wanted, the adapter resolves it inside the statement (`INSERT ... SELECT v.id FROM catalog.variants v WHERE v.sku = $3`, or a `LEFT JOIN ... ON o.external_id = $5`) rather than a second round trip; on read the row is joined back so the domain id returns, never the uuid.
- **A `jsonb` column needs `JSON.stringify`; `node-pg` does not serialise an object for you.** Passing a JS object as a `jsonb` parameter throws `invalid input syntax for type json`; `JSON.stringify(zone.polygon)` on the way in (and the parsed array on the way out) is the whole fix.
- **A join through an RLS-governed table silently narrows the result, so test the session shape, not just the query.** `membershipsFor` joins `identity.org_members` to `identity.users`; a non-staff session with only `app.org_id` set cannot see the user row, so the join returns nothing even though the membership exists. Scope the assertion to the session the caller really has (staff sees all; a customer sees their own membership) rather than assuming the join is transparent.
- **An integration spec's role needs the schemas it reads, including ones it only joins through.** The stock order source reads `sales.order_lines` (RLS-governed via the order) and joins `catalog`/`inventory`, so its test role is granted `USAGE`/table/sequence rights on `inventory, catalog, sales, identity`; a missing grant surfaces as `permission denied`, not as an empty result.
- **A hand-written schema is not the domain shape; add the bridge columns, do not reshape the domain.** The ads and partners stores needed columns the schema did not carry (a campaign's review workflow, a slot's day label, a document's name) and a notifications schema that did not exist. Migration 0017 only *adds* columns, adds an `external_id`/`partner_org_ref` bridge for the opaque string ids, and relaxes a `NOT NULL` the domain cannot satisfy (`partners.slots.slot_on` is a day label, not a date). Where a real foreign key is still wanted, the adapter resolves it inside the statement (`(SELECT id FROM identity.orgs WHERE external_id = $2)`), the same bridge T-046/T-047 use.
- **An RLS policy that tests a uuid must also test the domain-id bridge.** `ads.campaigns` and the partners tables key on a uuid `*_org_id`, but the domain carries an organisation id (`org-demo`). The rewritten policy matches either — `advertiser_org_id::text = current_setting('app.org_id', true) OR advertiser_org_ref = current_setting('app.org_id', true)` — so a row created by a domain id is still scoped to its owner.
- **A support-only table has no owner column, so its policy is staff-only.** The dispatch log (`notifications.messages`) and consent (`notifications.consent`) have no `org_id`, so their policy is `current_setting('app.staff', true) = 'on'` — a non-staff session sees nothing (default deny), which is what `db/tests/rls.sql` now asserts.
- **A store that must become async ripples into its callers, including a pure helper.** Making `ConsentStore`/`DispatchLog` async forced `decideConsent`, `DispatchService.send`/`list`, the three channel services, their controllers and the dispatch service's own `id` sequence (it read `this.log.list().length`) to `await`. Grep the whole service for the call sites before running the suite; a `.allowed` read on a `Promise` fails at type-check, not at runtime, so `tsc` catches it.
- **`describe.skipIf(!admin)` is the gate for a DB integration spec, and the role must be provisioned in the spec.** Each `*.sql-store.integration.spec.ts` builds `admin = new PgDb(DATABASE_URL)` only when the env var is set, then creates a `NOSUPERUSER, NOBYPASSRLS` role, grants the schemas it reads (including ones it only joins through, like `identity`), seeds two tenants, and connects as that role — a superuser bypasses RLS, so asserting through the admin connection would prove nothing. The spec cleans its own rows and drops the role in `afterAll`, so a rerun is idempotent.
- **The BFF reads a page by asking the owning service to resolve it, not by re-implementing the rule.** The storefront's curated sections come from `GET /gateway/bff/merchandising?page=`; the gateway forwards to commerce's `/commerce/merchandising/page`, which runs `resolveSection` against the catalogue, then the BFF only filters tiles by channel (`visibleSections`) and coerces the payload (`coerceSections`). A missing or failing merchandising read yields no sections rather than an error, and `home()` falls back to one section built from the catalogue, so a storefront page is never blank. `coerceSections` also accepts a bare array or a `{sections}` envelope and drops a codeless section or an unusable tile, so a shape change upstream degrades instead of throwing.
- **Two pre-existing gaps in the storefront read path (found during T-054, not yet fixed).** (1) `packages/api-client` calls `/commerce/*`, `/ads/*`, `/accounts/*` on the gateway base URL, but the gateway serves only `/gateway/*` and `/health` — there is no reverse proxy, Next route handler or rewrite anywhere, so those live reads cannot reach commerce in a deployed environment. (2) The merchandising store is in-memory only; unlike catalog there is no `merchandising.sql-store` wired through `selectStore`/`STORE_DRIVER`, so curated sections do not persist under `STORE_DRIVER=sql`. Also, the resolved merchandising read on commerce is gated by `merch:manage`, which no storefront caller holds — the BFF tolerates it today by catching and falling back, but a public read route on commerce is the clean fix. These need their own task cards. *(Gap 2 and the public-read route are fixed by T-062; gap 1 by T-061's reverse proxy.)*
- **A card's `files:` glob is a review hint, not the schema's name.** T-062 said `commerce.merchandising_sections`/`_items`, but there is no `commerce` schema (0001 creates one per bounded context) and the data-model doc, the domain types and the store comment all point at `catalog.merch_sections`/`merch_items`, which 0003 created for exactly this purpose. Check the schema the repo already has before writing a migration; landing over the existing tables (adding the `external_id` bridge) beat creating a duplicate pair under a new schema.
- **Editorial content is public to read and staff-only to write, and the read policy must match the domain rule.** A curated merchandising section is marketing the shop shows everyone, so `catalog.merch_sections` has separate `FOR SELECT`/`FOR INSERT`/`FOR UPDATE`/`FOR DELETE` policies: a write needs `app.staff = 'on'`, while a read with no staff setting sees only a section that is active and inside its half-open `[starts_at, ends_at)` window. A single `USING` policy would have doubled as the `WITH CHECK` and leaked a write to an anonymous caller. The policy's window is written to match the domain's `isSectionVisible`, and the service re-applies the rule, so the two cannot drift into showing different rows.
- **A serial-keyed table needs a sequence grant for the app role.** Adding RLS to `catalog.merch_sections` (a `serial` primary key) surfaced a latent gap: the application role had `USAGE`/`SELECT, INSERT, UPDATE, DELETE` on the schemas and tables but not `USAGE, SELECT ON ALL SEQUENCES`, so an `INSERT` failed with `permission denied for sequence`. The same grant was missing from `db/tests/rls.sql` and the `db/README.md` provisioning snippet; both now carry it.
- **A route that the storefront must reach cannot require a permission the storefront never holds.** The resolved merchandising read (`GET /commerce/merchandising/page`) was gated by `merch:manage`, so the BFF only worked by catching the 403 and falling back. Make the read public (the policy above still hides a draft) and declare it before `@Get(':id')` so `page` is not parsed as a section id; keep the management routes (`list`, `get`, `upsert`, `setItems`) behind `merch:manage`. Pin the split with a spec that reads the `PERMS_KEY` metadata per handler, so a later edit cannot silently re-gate the public route.
- **Generate brand icons and social cards in code; do not check in binary art.** The storefront's `icon`, `apple-icon`, `opengraph-image` and `twitter-image` are `next/og` `ImageResponse` route files, so the palette lives in the same `#1F3B2D`/`#B4492B`/`#D6A23E`/`#F4ECD8` literals as the design system and there is no PNG to keep in sync (the final logo is still TBD, so a binary would be a guess). The web manifest points its `icons` at `/icon`, and `next` picks the routes up automatically. `next/og` is a `function` on Next 14.2, not a class, so call `new ImageResponse(...)`.
- **A `Metadata`/`Viewport` import comes from `next`, not `react`.** `import type { Metadata, Viewport } from 'react'` type-checks as "no exported member" only because `react` has no such types; both come from `next`. The build catches it, so a per-app `tsc --noEmit` (the `lint` script) is the fast loop — run it per app, not just at the root.
- **Next writes `tsconfig.json`/`next-env.d.ts` on first build and the diff can be app-specific.** `next build` added `allowJs` and `.next/types/**/*.ts` to `apps/advertiser-portal` only, because the other five apps already had them; that is `next` normalising the app, so keep it. But it means a build in a dirty tree touches files you did not edit — check `git status` before staging.
- **The repo is not Prettier-clean, so format only the files you touched.** `pnpm format` (Prettier) rewrites dozens of pre-existing files; CI does not enforce it. Reformatting a file to add two lines churns its whole body (e.g. expanding one-line `<li><Link/></li>` into five lines), which buries the real change. `git checkout` the churned files and re-apply the small edit by hand.


- **A child table's policy must see the rows its own service writes.** `logistics.proof_of_delivery` had a policy that only followed `delivery_id`, but the driver app keys a proof by the stop (an order's domain id), never by the delivery uuid — so every row the service wrote was invisible to every session, staff included: write-only evidence. A policy that follows a foreign key must also follow the domain id the writing service actually has, and a test must read the row back through the same role that wrote it. The `db/tests/rls.sql` fixture proves default-deny, staff bypass and customer-owns-one for the table, not just the columns.
- **An excursion is evidence, not an error.** A probe reading outside the cold-chain band is recorded and flagged (`temperature_excursion`), never rejected: refusing it destroys the R638 evidence and leaves the offline queue retrying a capture that can never succeed. Only a reading no probe could produce (outside ±60 °C) is a refusal. Tell the two apart in the domain (`judgeCapture` returns `problems` for refusals and `excursion` for a flagged-but-stored reading), so the driver screen can warn without blocking the sync.
- **Idempotency per natural key, in the store, not the service.** Proof of delivery is once per stop, so the store's `save` is insert-or-nothing (`ON CONFLICT (stop_ref) DO NOTHING` then read back) and returns the record that is now stored. A replayed offline sync then returns the first capture instead of overwriting the signature, and the service needs no "already exists" branch. Do this in the adapter: a service-level check races between two concurrent syncs.
- **A durable queue and the "what have I done" ledger are two different stores.** Deriving the day's progress from the offline queue looks natural and is wrong: the queue is emptied by a successful sync, so the route resets to zero stops delivered every time signal returns — and `canCloseDay` could never be satisfied, because it requires an empty queue and a full route at the same time. Keep a small separate ledger (`day-ledger.ts`, keyed by stop id, delivered or refused) and clear it with the queue only when the day actually closes. A test that syncs the queue and then asserts progress survives is what catches this.
- **One module must own an IndexedDB schema.** IndexedDB only runs `upgrade` on a *version* change, so two modules opening the same database at v1 each with their own `upgrade` means whichever opens first creates only its own stores and the other finds them missing — intermittently, depending on import order. Declare every store in one place (`driver-db.ts`) and have both open through it. The `objectStoreNames.contains` guard alone is not enough; the shared opener is.
- **Generate the local encryption key non-extractable.** A per-install AES-GCM key stored as a `CryptoKey` with `extractable: false` can decrypt but cannot be read back by `crypto.subtle.exportKey`, so a script injected into the page cannot exfiltrate the key and decrypt a stolen queue offline. Assert `exportKey` *rejects* in the test, not just that round-tripping works — and assert the raw IndexedDB record does not contain the plaintext, since a seal that is never called still round-trips if you only test the happy path.
- **Mutation-test the security property.** Deleting the `seal(...)` call turned 7 queue tests red and nothing else would have noticed a "passing" suite that stored signatures in the clear. When a test claims a property (encrypted, ordered, scoped), break the property deliberately once and confirm the test fails.
- **A shared security rule belongs in `@ag/rbac`, and that path is gated.** The staff IP allow-list started in `apps/admin` (T-067) and had to be enforced by the gateway too (T-058). Rather than copy it, move it to `packages/rbac` — but note `packages/rbac/` is a gated path alongside `infra/`, `services/payments/`, `services/accounts/` and `db/migrations/`, so any change there needs the `human-approved` label. Plan for that gate when choosing where a rule lives; putting it in the "wrong" package to dodge the gate is how two copies start drifting.
- **Branch from `main`, not from the previous task's branch.** T-058 was cut while T-067 was still open, so its PR carried T-067's `infra/` files and failed the gate for changes it did not make. Rebase with `git rebase --onto main <prev-commit> <branch>`; expect a modify/delete conflict on any file the previous PR *added*, and drop it from the new PR (`git rm --cached`) since it belongs to the other PR.
- **A cookie session needs no guard change.** The guard resolves `Authorization: Bearer`; a `NestMiddleware` that copies the httpOnly cookie onto that header before any guard runs makes sessions work across the permission guard, the audit interceptor and every service, with `userFromRequest` untouched. Teach the middleware, not the auth package.
- **Verify the id token against the realm JWKS, and refetch on an unknown `kid`.** A pinned key breaks on every realm rotation. An unknown `kid` is what a rotation looks like, so force one refetch rather than waiting for the cache TTL — otherwise every sign-in fails for the length of the TTL after each rotation. Collapse concurrent fetches (`inflight ??= ...`) so a burst of sign-ins cannot stampede the IdP.
- **`createPublicKey({ format: 'jwk' })` is lenient.** A malformed RSA modulus does not throw; it yields a key that simply fails to verify. So "conversion succeeded" is not a meaningful assertion — assert that a token signed by the real key does *not* verify against the malformed one. Same lesson as the seal test above: assert the property, not the happy path.
- **OIDC `state` can be sealed rather than stored.** HMAC-signing `{returnTo, nonce, PKCE verifier, expiry}` into the `state` parameter means any stateless replica can validate a callback, which is what a rolling deploy requires. A server-side store would pin the callback to the replica that started the login.
- **`prompt=login` on a staff IdP.** Without it a shared office browser silently signs the next person in as the last one.
- **Build dependent workspace packages before running a sibling's tests.** `@ag/rbac` and `@ag/nest-auth` resolve to `dist/`, so a new export is invisible to `@ag/gateway`/`@ag/admin` tests until `pnpm --filter <pkg> build` runs. The failure looks like `x is not a function` or a missing export, not a stale-build error.
- **`infra/` is a gated path: a PR touching it fails CI until a human adds `human-approved`.** The `agent-gate` workflow greps the changed paths against `^(db/migrations/|packages/rbac/|services/payments/|services/accounts/|infra/|\.github/)`. An agent cannot self-approve, so plan for a human step rather than retrying the gate.
- **Next.js middleware is where a front-end access rule belongs, not the Nest guard.** The admin portal is served by Next.js, so a gateway guard never sees the page request; `apps/admin/middleware.ts` runs on the edge runtime before any page or route handler. Keep the rule itself in a plain, unit-testable module and the middleware a thin adapter — it now lives in `@ag/rbac` (see the note above) so the gateway can enforce the same rule.
- **Exempt `/health` from any front-end access filter.** The platform readiness probe comes from Northflank's network, not the office, so an IP allow-list that covers `/health` fails the probe and restarts a perfectly healthy service. The health route returns no data, so exempting it costs nothing.
- **An empty allow-list must fail open only for local development, and the deploy contract must say so.** `isIpAllowed(ip, [])` returns `true` by design; that is right for a laptop and catastrophic in production, where it silently leaves a portal holding every permission open. Assert the *wiring* (template argument → secret group → `process.env`) in `infra/deploy.spec.mjs`, since no unit test of the rule can catch a missing environment variable.
- **Two compose files when two port conventions collide.** `koyeb-compose.yaml` is all-Python on `:8000` and the contract test asserts that for every service in it; staging runs Node on `:3000`. Adding staging to the same file would force weakening the assertion for both. A separate `koyeb-staging.yaml` with its own test keeps each check sharp.
